### TC-19 The clarion-assistant /lsp-diagnostics skill runs end to end with the IDE closed: FAIL (2026-09-19 01:05)

The worker confirmed `get_solution_info` ready true, then invoked `clarion-assistant:lsp-diagnostics` seconds after TC-17's restart (server pid 21656, banner 05:28:20Z; skill started 05:29:30Z). The skill ran six parallel subagents, each walking a 141-145 file chunk and recording results by hand into `diag_result_N.json`: 866 `lsp_diagnostics` calls, 0 tool errors, 0 pending, about 31 minutes. Every tool it called (`get_solution_info`, `lsp_debug_status`, `get_project_source_files`, `lsp_diagnostics`) was known. The summary line was in the required form.

The worker withheld the report because its attribution was wrong in a detectable subset: 6 of the 99 files with diagnostics carried a diagnostic line beyond the file's length, each holding the diagnostics of the file immediately before it in the same chunk (for example `reg_DEVICE_CustDisplay.clw`, 385 lines, reported the `OROF` error at line 571 that belongs to `reg_DEVICE_CloseDevices.clw`; `reg_ITEM_DISC_CheckValid.clw` reported `reg_ITEM_DISC_Discount.clw`'s two errors). Single sequential calls on the same server returned the correct pairing for all four files.

Judgement: FAIL on the expected text's "the skill completes and prints a summary": the summary was produced from misattributed data.

Root cause analysis (orchestrator):

1. **The file swap is not in the MCP.** `probe-streams.mjs` replayed the same pattern with scripted calls (server killed, then six parallel streams over the worker's own chunk lists, every call through the MCP): 866 calls, 0 errors, **0 results with a line beyond the file's length**, and a sequential re-check of the 169 files with diagnostics or preceding one agreed on all but 2. The MCP keys publishes, versions and waits by URI, so a swap cannot arise there; the swaps came from the subagents transcribing tool output into their result files (the skill leaves collection to the model, and the worker chose six parallel subagents to "batch efficiently"). That is a property of the plugin's skill design, recorded below as an observation for its maintainers, not fixed here.
2. **Real MCP defect found by the replay: diagnostics taken while the server is still indexing are provisional but were reported `complete: true`.** The two mismatches were files whose parallel answer carried "'Exits_OK' is not declared in this file" style warnings and whose settled answer was empty. The v1.0.2 server defers its semantic validators while `solutionPipelineReady`/`sdiPipelineReady` are false, then runs them before the file relationship graph exists (spurious "not declared"), and finally re-validates every open document once its background work ends; each republish carries the same document version, so the MCP recorded the correction silently and the *next* call returned it. Seven replay results also came back `complete: false` because only the structural publish arrived inside 20 s. The server exposes the window through `clarion/graphStatus` (`building`, then `built`), which is also what gates its own "still indexing" hover placeholder.

Fix (this repository): `LspClient.indexing` is set on `open_solution` and cleared by `clarion/graphStatus` `built`; `lsp_diagnostics` reports `indexing` and keeps `complete: false` while it is true; `lsp_debug_status` shows the flag; descriptions, README and the user guide updated; fake server sends `graphStatus` (`FAKE_INDEXING=1` never finishes); new test "reports complete:false and indexing:true until the server's background graph is built". 40 tests pass. Verified on the real solution (`probe-indexing.mjs`): 7 s after a restart the three probe files answered `indexing: true, complete: false`; 15 s later `indexing: false, complete: true` with the settled lists. Version bumped to 0.1.1 (the fix is not in the published 0.1.0).

Observations for the record (not defects in this repository):
- The skill's per-file collection is done by the model; over 866 files a transcription slip is likely, and the skill has no self-check. A cheap guard would be to reject any recorded diagnostic whose line is beyond the file's length, or better to let the MCP aggregate a whole solution in one call so no model copies 866 results. Upstream: ClarionLive/clarionassistant-marketplace, skill `lsp-diagnostics`. Not filed.
- `get_project_source_files` lists 866 entries for 858 unique paths: `VSAPIERR.CLW`, `VSA_TERM.CLW` and `VSA_ENUM.CLW` belong to several projects and appear once per project, as designed.
- Run 3's TC-19 report (2026-09-18) was produced the same way and is suspect for the same reason; its verdict stands on "completes with a summary and known tools", which it did, but its per-file numbers should not be quoted.

Run 4 stops here. The rerun (Run 5) needs the worker session restarted on a build that contains the fix (local `dist` at the fix commit, or npm 0.1.1 once published).
