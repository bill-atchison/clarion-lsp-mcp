It declares engines.node: "^22.12.0 || ^24.0.0 || >=26.0.0", which is stricter than this project's own engines.node: ">=20". npm install only warned (EBADENGINE), and npx vitest run / npx tsc --noEmit both ran correctly on the actual Node v20.18.1 in this sandbox for every task (verified after every task, see test summary in the final report). Task 2

test/clarion.test.ts: added delete process.env.CLARION_ROOT; to beforeEach (the plan's version only cleared it in afterEach). This sandbox's Windows host has a real Clarion 12 install with CLARION_ROOT=C:\Clarion12 set in the ambient shell environment (for the real clarion-assistant plugin). Without clearing it in beforeEach too, the very first test ("picks the highest version...") read the host's real CLARION_ROOT instead of the temp-directory fixture and failed by finding C:\Clarion12 instead of the test's own Clarion12 under the temp drive. This is a root-cause fix to make the test hermetic against the host environment, not a behavior change to findClarionRoot itself (whose contract, "CLARION_ROOT env var beats auto-detection," is exactly what afterEach already assumed by cleaning it up).

Task 4

test/lsp.test.ts, "times out a hung request": the plan's version used { requestTimeoutMs: 200 } and asserted /timed out|not found/. Two real problems on this machine:

  • requestTimeoutMs also bounds the initialize request that LspClient.start() sends as part of the handshake. Spawning the fake server (cold Node process + ESM import of vscode-jsonrpc/node) and completing the initialize round trip measured 400–700 ms on this host, well over 200 ms, so start() itself threw ("initialize timed out after 200 ms") before the test ever reached the assertion it cared about.
  • The installed vscode-jsonrpc@9.0.2 rejects a request for an unregistered method with code -32601 and message "Unhandled method <name>", not a message containing "not found" as the plan assumed.

Fix: raised requestTimeoutMs to 5000 (generous headroom for the handshake; the method-not-found rejection itself still returns in well under 50 ms so the test stays fast) and widened the assertion regex to /timed out|not found|Unhandled method/i. This does not change LspClient's behavior or the timeout contract in the spec (15s/3s/30s in the real implementation are untouched) — it only fixes a test fixture value and assertion wording that were tuned for a faster/different environment than this one.

Task 6

positional() and the inline lsp_document_symbols handler in src/tools.ts: the plan's version called checkFile(a.file_path) before withClient(s, ...). That makes a missing-file error win over a missing-solution error when both are true, but the "refuses when no solution is open" test calls lsp_hover with a file path (C:\x.clw) that also does not exist, and expects the "No solution open. Call open_solution first." message. Fixed by moving checkFile inside the callback withClient invokes, so the solution-open guard (which throws before calling the callback at all) is always checked first, and the file-existence guard second, before anything reaches the server. This matches the spec's error table, which lists "Any tool before open_solution" as its own row ahead of "File path outside the solution or missing." No behavior changed for the case both plan and tests actually exercise together (open solution + missing file): checkFile still runs, and still throws, before openDocument ever touches the server.

Task 6

DocSymbol.location in src/tools.ts: the plan typed it as { range: Range }, then cast it to { uri: string } in lsp_find_symbol to read .uri. TypeScript strict mode rejected that cast (TS2352: the two object types do not overlap enough to be reinterpreted). Real LSP SymbolInformation.location (what workspace/symbol actually returns, including the fake server's) is a Location, { uri, range }, so the type was widened to { uri: string; range: Range } and the cast removed in favor of the properly typed field. No runtime behavior changed; this only fixes the type to match the shape already flowing through it.

Task 6

test/harness.ts: raised the fake-server client's clientOpts from { readyTimeoutMs: 2000, requestTimeoutMs: 2000, diagnosticsTimeoutMs: 1000 } to { readyTimeoutMs: 5000, requestTimeoutMs: 5000, diagnosticsTimeoutMs: 2000 }. Running npx vitest run for the whole suite (all three test files, vitest's parallel workers) hit one flaky failure in "opens a solution and reports it" (ready came back false) that did not reproduce running test/tools.test.ts alone; the same cold-spawn-plus-ESM-import latency noted for Task 4 gets worse under the CPU contention of several test files' child processes running at once. The 2000 ms budget was occasionally not enough. Confirmed stable across three consecutive full-suite runs after raising it. This only affects test fixtures, not the 15s/3s/30s timeouts LspClient itself uses against a real server.

Task 7

lsp_diagnostics: applied the same precedence fix as Task 6 (moved checkFile inside the withClient callback rather than before it), for consistency with the other file-taking tools and so "no solution open" always wins over "file not found" here too. No test exercises this exact combination for lsp_diagnostics, but leaving the ordering inconsistent between tools with an otherwise identical guard shape would be its own latent bug.

Task 9 — deviation, with evidence

The plan's "reports an error for a missing include after an edit" test does not match how the real server's diagnostics actually work. The plan edited in INCLUDE('DoesNotExist.inc'),ONCE and expected lsp_diagnostics to report a count > 0. Against the real Clarion 12 addin server this always came back { pending: false, count: 0, diagnostics: [] }, confirmed reproducible with a longer (20s) wait and with cross-checks using a second, unrelated defect (an undeclared-variable reference), which also came back empty. Root cause, found by reading the shipped server source (out/server/src/server.js and out/server/src/providers/DiagnosticProvider.js / out/server/src/providers/diagnostics/MissingIncludeDiagnostics.js):

  • The diagnostic named missingIncludes does not check whether an INCLUDE statement's target file exists on disk. Its own doc-comment: "Detects variables declared with a user-defined class type that is not included in the current file or its MEMBER parent" — e.g. st &StringTheory without an INCLUDE('StringTheory.inc'). A genuinely-missing include *file* is not a diagnostic category this server emits at all; presumably that surfaces only at actual compile/build time, outside the LSP's scope.
  • Even if it were the right check, missingIncludes is one of seven async validators (server.js's validatorThunks) that are deferred until two internal flags, solutionPipelineReady and sdiPipelineReady, are both true. sdiPipelineReady flips only after a background chain kicked off from the clarion/updatePaths handler: build the Structure Declaration Index, sleep exactly 2000 ms, build the FileRelationshipGraph, build the ReferenceCountIndex, then re-validate every open document. This chain starts after clarion/solutionReady is sent (the notification this MCP's ready: true is based on), so "ready" and "async diagnostics available" are two different milestones with no notification exposed for the second one. A document opened between them gets queued in the server's own deferredAsyncDocs set and is only revalidated whenever that chain finishes — which our client has no way to await.
  • undeclaredVar (the other candidate we probed) is separately gated by serverSettings.undeclaredVariablesEnabled, which this MCP deliberately never sets (per the spec: "omitted, so the server keeps its own defaults") — and the server's default is off, confirmed empirically (an undeclared-variable reference produced no diagnostic either).

What was verified to actually work, and what the test now asserts instead: the sync validators in DiagnosticProvider.validateDocument (structure terminators, case/ execute/file structures, etc.) always run immediately, regardless of sdiPipelineReady, because they need no cross-file resolution. Editing in an unterminated CASE (no matching END) reliably produced, within 3 seconds, on the very first try, every time across three consecutive runs:

[{
  "severity": 1,
  "range": { "start": { "line": 10, "character": 2 }, "end": { "line": 10, "character": 6 } },
  "message": "CASE statement is not terminated with END or .",
  "source": "clarion"
}]

test/integration.test.ts's test was renamed to "reports an error for an unterminated structure after an edit" and now edits in that CASE/no-END instead, asserting both count > 0 and the exact message substring above. This is a test-only change: no production code (clarion.ts, lsp.ts, tools.ts) needed a fix, because lsp_diagnostics was already correctly relaying whatever the server published — the plan's assumption about what the server would publish for that particular edit was simply wrong. Per the task instructions, the assertion was changed to match verified real behavior rather than weakened or skipped.

Live-run bug: redirected source files reported as unresolved

2026-09-17 live run

Symptom. On a real 38-project solution (zPOS_Register, 866 source files under a redirected _Source folder), get_project_source_files returned every file as unresolved. Diagnostics still worked because the agent opened files by absolute path.

Root cause. The server's RedirectionFileParserServer.parseRedFile() treats serverSettings.redirectionFile as a bare file name: it tries path.join(projectDir, redirectionFile), then path.join(redirectionPaths[0], redirectionFile). The spec and Task 3 passed a full path, so both joins produced a nonexistent path (C:\proj\C:\proj\Clarion110.red), the parser returned zero entries, and every redirected lookup (clarion/findFile, getSearchPaths, getClwDirectories) collapsed to the project folder. The Task 9 fixture never caught it because its main.clw sat beside the .cwproj.

Fix. buildPaths() now sends redirectionFile as the basename and keeps the full path in a new redirectionFilePath field, which the server ignores and the tools use for reporting. The fixture now keeps main.clw in _Source behind a HelloLsp.red, so the integration test reproduces the failure and proves the fix. Re-probed the real solution afterwards: 38 projects, 866 resolved, 0 unresolved.

Spec correction. The spec's payload example shows a full path for redirectionFile; the server contract is a file name resolved per project directory with redirectionPaths[0] as fallback.

Live-run finding: cross-project definitions, and relative paths

2026-09-17 live run

Symptom. TC-08 asked for the definition of reg:WIN:ShowExits() from _Source\reg_ITEM_GetAction.clw (project regItem) and got []. The PROCEDURE lives in _Source\regWindow.clw (project regWindow) with its prototype in libsrc\regWindow.inc.

Evidence. Probed through the tools at 6 s, 59 s and 122 s after ready. A same-project cross-file call (reg:ITEM:CashOutExists()) resolved every time to _Source\regItem.clw line 64 (4.9 s cold, 35 ms warm). The cross-project call returned [] and hover returned "" every time, while workspace/symbol "ShowExits" found the prototype in libsrc\regWindow.inc line 51. So the MCP plumbing is sound; the server does not connect a prefixed call-site label to a procedure in another project. Not an MCP defect; documented in the user guide's troubleshooting table and TC-08 now asks for a same-project call.

Follow-up (2026-09-18). Dug into the server with its own tokenizer run in-process. It is not a cross-project limit at all: (1) DocumentStructure.processShorthandProcedures returns early when a file has no MAP, so an .inc holding prototypes under SECTION('PROTOTYPES') gets no MapProcedure tokens and the MAP include expansion copies them unclassified; (2) pre:fix:name( tokenizes as StructurePrefix, colon, Function, so the shorthand label is name while the call-site word keeps its colons; (3) the MEMBER-parent path in DefinitionProvider never consults included tokens. A three-file patch (docs/server-patches/) fixes all three; verified on a patched copy and then on the installed server: definition from the caller now lands on libsrc\regWindow.inc line 51 and hover links through to REG_WIN_SHOWEXITS.CLW. Filed upstream as msarson/Clarion-Extension#593 with the diff, after confirming the same code on branch version-1.0.5.

Warm-up. The first workspace/symbol after ready on this 866-file solution exceeded the 15 s request timeout; at 59 s it took 2.0 s. Documented as expected behaviour rather than raising the timeout.

Relative paths. The tester passed file_path "_Source\reg_ITEM_GetAction.clw". checkFile resolved it against process.cwd(), which happens to be the solution folder when Claude Code launches the server from there, but is the repo folder in tests and undefined in other hosts. Now resolves against the open solution's folder; covered by a new tools test (37 tests total).
