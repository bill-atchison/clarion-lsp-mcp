Brainstorm: expose the addin-bundled LSP to agents outside the IDE, distributable to other machines and people.

Overview

The Clarion Assistant IDE addin ships a full Clarion language server: a Node application at <ClarionRoot>\accessory\addins\ClarionAssistant\lsp-server\ with its own node.exe and entrypoint out\server\src\server.js. Today only the running IDE can use it. The addin starts the server, sends it the solution's paths, and exposes eleven MCP tools to Claude Code that the clarion-assistant plugin skills already depend on.

This project is a standalone MCP server, clarion-lsp-mcp, that does what the addin does for the language server, without the IDE. It finds the Clarion install, starts the bundled server, tells it which solution to index, and exposes the same eleven tools plus one to open a solution. Any MCP host that can launch a command works: Claude Code, Codex, Grok, or anything else.

Goals

  • Same tool names and result shapes as the IDE's MCP, so existing skills such as /lsp-diagnostics run unchanged with the IDE closed.
  • Install on another machine with one npm command and one JSON snippet per host.
  • No redistribution of the language server. The MCP locates an existing Clarion install that has the addin.

Non-goals

  • Bundling the server or node.exe. Needs a Clarion install with the Clarion Assistant addin.
  • Mutating project structure. No addSourceFile, no addModuleWithProcedure, no applying renames. Agents already have file tools, and the IDE owns project files.
  • Building, generating, or anything touching .app files. This is read-only code intelligence.
  • Non-Windows hosts. Clarion is Windows only.

Chosen Approach

Thin proxy. Spawn the bundled server as a child process, speak JSON-RPC over stdio with vscode-jsonrpc, and translate each MCP tool into one LSP request. One server per MCP process, started lazily on the first open_solution.

Rejected: vscode-languageclient (built for the VS Code host, far more surface than needed) and hand-rolled JSON-RPC framing (re-implements header parsing and request correlation that vscode-jsonrpc already does).

Components

clarion.ts: finding Clarion and the solution

findClarionRoot(override?) returns the first of:

  1. CLARION_ROOT env var, or the clarion_root tool argument, if set. Fails loudly if it lacks the server.
  2. Every C:\Clarion* directory that contains both bin\Clarion.exe and accessory\addins\ClarionAssistant\lsp-server\out\server\src\server.js, sorted by the file version of Clarion.exe descending. Highest wins.

Version comes from Clarion.exe's file version via one PowerShell call ((Get-Item ...).VersionInfo.FileVersion). No registry lookups: the addin folder is the only thing that proves the server exists.

findSolution(explicit?, cwd): an explicit path must exist and end in .sln. Otherwise glob *.sln in cwd only (no recursion). Exactly one match is used; zero or many is an error whose message lists the candidates. Note that hosts differ in what cwd the MCP process receives, so the README tells users to pass a path when in doubt.

buildPaths(root, solution, configuration) produces the clarion/updatePaths payload. The server parses .sln, .cwproj, and .red itself, so the MCP only supplies locations:

{
  solutionFilePath: "C:\\Work\\App\\App.sln",
  redirectionFile:  "C:\\Work\\App\\App.red",   // .red beside the .sln if one exists,
                                                // else the first *.red in <root>\bin
  redirectionPaths: ["C:\\Clarion12\\bin"],
  libsrcPaths:      ["C:\\Clarion12\\libsrc\\win", "C:\\Clarion12\\libsrc"],
  projectPaths:     ["C:\\Work\\App"],          // [0] MUST be the solution directory; the
                                                // server returns silently if this is empty
  macros:           { ClarionRoot: "C:\\Clarion12", bin: "C:\\Clarion12\\bin",
                      redname: "App.red" },
  configuration:    "Debug",
  clarionVersion:   "12.0.14625",
  defaultLookupExtensions: [".clw", ".inc", ".equ", ".eq", ".int"]
}

The boolean feature flags the server accepts (undeclaredVariablesEnabled, inlay hints, code lens) are omitted, so the server keeps its own defaults. Code lens is never requested by the MCP, so its cost is not paid.

lsp.ts: the client

LspClient owns one child process and one vscode-jsonrpc MessageConnection.

  • start(root): spawn <root>\...\lsp-server\node.exe out\server\src\server.js --stdio with cwd set to the lsp-server folder, so its node_modules resolve. Send initialize with rootUri = solution directory and minimal client capabilities, then initialized.
  • openSolution(paths): send clarion/updatePaths, then await clarion/solutionReady. Resolve early with { ready: false } after 30 seconds; the server continues indexing and later calls just work.
  • openDocument(path): read the file from disk, send textDocument/didOpen if not already open, or textDocument/didChange with full text if the on-disk content differs from what was last sent. This is how edits made by the agent's own file tools become visible to the server.
  • request(method, params) and notify(method, params): thin pass-throughs. Every custom clarion/* call goes through these, which is the plumbing that makes future extras one-liners.
  • diagnostics: a Map<uri, Diagnostic[]> fed by textDocument/publishDiagnostics, plus a waitForDiagnostics(uri, ms) that resolves on the next publish for that uri or times out.
  • stderr ring buffer of the last 50 lines, and counters of notifications received, for lsp_debug_status.
  • stop(): send shutdown, exit, then kill after 2 seconds if still alive. Called on MCP transport close and on SIGINT.

tools.ts: the tool surface

Line and character are zero-based, as in the IDE's tools. File paths are absolute Windows paths; the MCP converts to file:/// URIs and back so agents never see URIs.

Every position tool calls openDocument first. lsp_diagnostics treats a timeout as pending: true, never as clean, matching the IDE contract the skills rely on.

get_project_source_files is the one tool that composes two server calls. clarion/getSolutionTree returns projects with name, path, and guid but empty sourceFiles; clarion/getProjectFiles({ projectGuid }) returns { files: [{ name, relativePath, project }] }. The MCP joins project.path and relativePath; if that file does not exist on disk (redirected source), it asks clarion/findFile for the resolved path. Files that still cannot be resolved are reported under an unresolved list rather than dropped.

index.ts: the MCP server

McpServer from the SDK over StdioServerTransport. Registers the twelve tools with zod schemas and one-line descriptions copied from the IDE reference so agents pick them the same way. The server instructions string tells the agent to call open_solution first and that lines are zero-based. Nothing else: no resources, no prompts.

Data Flow

Startup, the only real sequence in the system:

  1. Host launches npx clarion-lsp-mcp. The MCP registers tools and waits. No child process yet.
  2. Agent calls open_solution (or a skill calls lsp_start). The MCP resolves the Clarion root and the .sln, builds the payload, spawns the server, and sends initialize, initialized, clarion/updatePaths.
  3. The server parses the .sln, .cwproj files, and the .red, indexes sources, and emits clarion/solutionReady. The MCP returns ready: true, or ready: false after 30 seconds.
  4. Agent calls lsp_diagnostics on a file. The MCP reads the file, sends didOpen, waits for publishDiagnostics on that uri up to 3 seconds, and returns the cached list.
  5. Agent edits the file with its own tools and calls lsp_diagnostics again. The MCP sees the disk content changed, sends didChange with full text, waits, returns fresh diagnostics.

Calling open_solution again with a different solution stops the server and starts over. Same solution: re-sends updatePaths only.

Error Handling

SituationBehaviour
No Clarion install foundopen_solution returns an error naming the folders searched and how to set CLARION_ROOT.
Install found but no addin serverError says the Clarion Assistant addin is required and where it was expected.
Zero or several .sln in cwdError lists what was found and asks for solution_path.
Any tool before open_solutionReturns { error: "No solution open. Call open_solution first." }. No implicit start, so the agent learns the contract.
File path outside the solution or missingPosition tools return an error; nothing is sent to the server.
Server exits or crashesClient marks itself dead and keeps the stderr tail. The next tool call runs the full start() again (spawn, initialize, initialized), re-sends updatePaths, re-opens the requested document, and retries once. A second failure is returned to the agent with the stderr tail.
Request hangsEvery LSP request has a 15 second timeout, diagnostics 3 seconds, solution ready 30 seconds. Timeouts are reported as such, never as empty results.
Host closes the transportstop() runs; the child never outlives the MCP.

All tool errors are returned as MCP tool results with isError: true and a plain message, not thrown, so every host renders them the same way.

Risks

  • Server contract drift. The clarion/updatePaths field names and clarion/getProjectFiles shape are read from the shipped build, not a published API. A future addin release may change them. Mitigation: the integration test pins the local install, and lsp_debug_status exposes the server's stderr so drift is diagnosable.
  • Redirection file choice. Picking "the .red beside the .sln, else the first in bin" is a guess at what the IDE does. The .cwproj may name a different one. If the integration test shows missing includes, add a redirection_file argument to open_solution rather than growing heuristics.
  • Working directory ambiguity. Hosts pass different cwd values to MCP processes. Documented; explicit solution_path is the escape hatch.
  • Large solutions. Indexing a big solution can exceed 30 seconds. The MCP returns ready: false and tools keep working as the index fills, which is the same experience the IDE gives. Because a malformed payload also produces silence from the server, ready: false includes the stderr tail so a rejected payload is distinguishable from a slow index.

Self-review

  • No placeholders. Every field in the payload is sourced from the server's updatePaths handler as shipped in Clarion 12.
  • Consistent: the tool table, data flow, and error table agree on when the server starts (only on open_solution or lsp_start) and on the three timeouts.
  • Scope fits one plan: four source files, two test files, one fixture, one README.
  • Ambiguity resolved: "same shapes as the IDE" is pinned by the tool table; where the IDE's exact JSON was not visible, the shape chosen is the one its skills consume.
